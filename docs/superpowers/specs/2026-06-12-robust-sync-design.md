# Надёжная синхронизация Supabase (last-write-wins + tombstones)

Дата: 2026-06-12. Статус: дизайн одобрен пользователем в чате.
Ограничение: коммит локально, push — только по отдельному согласию.

## Проблема (подтверждена в коде)

`js/cloud.js`:
- `cloudDelete(id)` → `flushQueue` делает `delete().eq("id",id)` (жёсткое
  удаление строки). Другое устройство, у которого машина ещё есть, в
  `fullSync` видит её отсутствие в облаке (`toPush=filter(!cloudIds.has)`)
  и **заливает обратно** → воскрешение удалённой машины.
- `fullSync` не сравнивает свежесть: `S.warehouse=cloudCars` и upsert
  всегда перетирают без учёта, какая версия новее. При конфликте правок
  с двух устройств побеждает «кто синхронизировался последним», а не
  «кто отредактировал последним».

## Решение

Last-write-wins по метке времени + tombstones. Схему Supabase менять не
нужно: `cars(id text, data jsonb, updated_at timestamptz)` остаётся;
`updatedAt`/`deletedAt` живут внутри `data`.

### 1. `updatedAt` на каждой машине
- ISO-время последнего изменения. Ставится при ЛЮБОЙ правке.
- Хелпер `touch(car)` (js/cloud.js): `car.updatedAt=new Date().toISOString()`.
  Вызывается ДО `saveWH()` в каждой мутации: `addToWH`, `saveCarEdit`,
  `doSell`, `retStock`, и в undo-возврате `delCar`.
- `normalizeCar` (js/core.js) сохраняет поле:
  `updatedAt: typeof c.updatedAt==="string"?c.updatedAt:""`.
- Старые машины без метки → `""` (древнейшая). При первом синке метки у
  всех пустые → равенство → берётся облачная версия (как сейчас), без
  массовых перезаписей. Отслеживание стартует с первой новой правки.

### 2. Tombstones вместо жёсткого удаления
- `cloudDelete(id)` фиксирует момент удаления и кладёт в очередь
  `{t:"d", id, ts:<ISO>}`.
- `flushQueue` для `t:"d"` делает upsert надгробия, НЕ delete:
  `{id, data:{id, deletedAt:ts, updatedAt:ts}, updated_at:ts}`.
- Строка остаётся в облаке как надгробие; другое устройство узнаёт о
  факте и времени удаления. Надгробия крошечные; авто-чистку не делаем
  (риск воскрешения у долго-офлайн устройства), оставляем на будущее.

### 3. Слияние в `fullSync` (ядро)
1. `flushQueue()` — сперва отправляем накопленные локальные операции.
2. `select id,data` — приходят и машины, и надгробия.
3. Надгробие определяется по `data.deletedAt` ДО `normalizeCar`
   (у надгробия нет `entries`, `normalizeCar` его бы отбросил) — поэтому
   облачные записи кладём в `cloudMap` сырыми.
4. Для каждого `id` из объединения `cloudMap` ∪ локального склада:
   - `cloudTs = data.updatedAt || data.deletedAt || ""`,
     `localTs = car.updatedAt || ""`.
   - облако-надгробие И `cloudTs >= localTs` → удалить локально
     *(чинит воскрешение)*;
   - локальная новее (`localTs > cloudTs`) → `pushCar(localCar)`
     (upsert с ЕЁ меткой, без `touch`);
   - иначе облачная новее/равна: если надгробие — удалить локально;
     иначе принять `normalizeCar(cloudData)`;
   - только облако: надгробие игнор, иначе принять;
   - только локально → `pushCar`.
5. `saveWH(); markBackup(); render()`.

`pushCar(car)` — внутренний upsert БЕЗ `touch`: метку двигает только
действие пользователя, иначе сравнение свежести сломается. (Текущий
`cloudUpsert`, наоборот, ставит свежую метку — он для пользовательских
мутаций.)

### Что не ломается
- Офлайн-очередь правок (autoCalc_queue) — как раньше: flush-then-merge.
- Прод-данные: первый синк безопасен (пустые метки → no-op).
- Undo удаления: `touch`+`cloudUpsert` оживляют машину свежей меткой,
  которая (как самое позднее действие) победит надгробие.

## Проверка
Браузер с моком `CL.sb` (две «реплики» облака в памяти):
- удаление на A → надгробие → B не воскрешает, убирает у себя;
- правка на B новее → побеждает старую облачную;
- конфликт: одновременные правки → новее выигрывает;
- офлайн-очередь доходит после онлайна;
- старые машины без `updatedAt` не перетираются на первом синке;
- undo удаления оживляет машину.
Затем ревью-workflow по диффу. Коммит локально (без push).
